# Report pipeline audit — 2026-09-22

Read-only audit of checkout `019fa14`, following the requirements attachment. No product code, schema, questions, or template changed. Paths below are repository-relative to `/Users/dan/Desktop/perfect ppi/ppi-standalone`.

## Main conclusions

1. The requested two-page inspection PDF is a renderer and data-contract change, not merely a new prompt. Today `src/lib/pdf/standardized-report-pdf.ts:20` builds a single stream of text; `:99` appends all sections and findings, and `:120` hands it to `simple-pdf`. `src/lib/pdf/simple-pdf.ts:49` wraps and paginates by remaining vertical space. It supports regular/bold text only, US Letter 612×792 points (`:8`), and has no fixed page break, boxes, drawings, color/status selection, wheel/body graphic, or page-count guarantee. More questions and findings produce more pages. It also sanitizes non-ASCII text to hyphens (`:14`).
2. Images are already sent to the Stage 1 model; this is not a brand-new capability. What is missing is structured per-wheel extraction, field provenance, confidence/review state, deterministic status rules, and pre-submit confirmation of model suggestions.
3. There are two separate PDF artifact types today: inspection report and VSC determination. The new two-page inspection report should replace only `inspection_report_pdf`; do not mistake VSC's separate PDF for the requested analysis page.
4. `valuation` in the request needs clarification. Source searches found no vehicle appraisal, market-price/repair-cost estimate, Jev client, or Typesafe client. Current report analysis assigns condition/severity; current VSC stage assigns warranty eligibility. Warranty plan prices are fixed tiers, not vehicle valuations.
5. Question prompt text is effectively a key in several layers. Renaming questions or introducing mm units without coordinated updates can change warranty outcomes and validation silently.

## Current execution path

### Collection and submission

- Complete has 12 sections; Dents & Tires has only `wheels_tires` and `body_damage` (`src/features/ppi/constants.ts:9`, `:28`). Complete excludes no implied scope restriction; Dents & Tires explicitly omits brakes, engine, interior, road test (`:24`). The existing product name is Dents & Tires, not Dents & Scratches.
- Complete collects four tread depths, one estimated brake-pad-life selection, one whole-car uneven-wear yes/no, and an optional rotor observation (`constants.ts:285–323`). Dents & Tires has four numeric tread questions requiring a photo each, a free-text combined rim/tire problem field, and six optional free-text body-area fields (`constants.ts:505–564`). Neither has structured DOT date, tire size/load index/speed symbol, tire pressure/leak check, four-grade dry rot, corner-specific uneven wear, tire damage flags, placard capture/comparison, or a final truthfulness attestation.
- `src/features/ppi/actions.ts:523` validates required answers and required per-answer images before calling `submit_ppi_atomic` (`:588`). `supabase/migrations/20260907140000_inspection_scope_and_answer_photos.sql:88` is the current atomic submission function, enforcing required answers, constrained values, and photos in SQL too. Its signature only accepts submission ID and submitted timestamp; it does not attest anything (`:88–91`).
- Tread inputs are whole integers from 0 to 32 by exact prompt (`src/features/ppi/answer-validation.ts:3`, `:25`, `:61`). SQL repeats those exact four prompts (`20260907140000...sql:153`). A mm workflow must deliberately change both validation implementations and warranty normalization.
- Web submit has no request payload (`src/app/api/ppi/submissions/[id]/submit/route.ts:11–20`); it enqueues durably after submission (`:30`) and runs a latency optimization with Next `after` (`:44`). Add attestation at UI, API/action, and transaction boundary together. Do not confuse inspector credential certification with the user's requested truthfulness certification.
- Resubmission deep-copies current answers/media into a new submission version (`src/features/ppi/actions.ts:607`, `:623`, `:653`). Any future attestation and reviewed extraction should be invalidated/reconfirmed for revised answers, rather than silently copied as already certified.

### Queue and retries

- `src/features/outputs/worker.ts:46` reconciles submitted inspections missing jobs; `:59` atomically claims with a lease. The worker processes jobs sequentially (`:80`). Success/failure and structured error categories are recorded; retries use backoff until permanent failure or max attempts (`:108–155`).
- Output worker HTTP route is Node runtime, up to 300 seconds, default 3 claimed jobs (`src/app/api/internal/workers/outputs/route.ts:6–10`, `:24`). Vercel invokes it every five minutes (`vercel.json:5–6`). Lease is 600 seconds and max attempts 5 (`src/features/partner/constants.ts:103–106`). New model stages must fit these shared limits or become separately checkpointed jobs; simply adding multiple sequential model calls risks timeout.
- Retry preserves output version and existing artifacts; regeneration creates a new immutable version (`src/features/outputs/actions.ts:64–106`). A rollout should use new versions, not rewrite already-issued bytes/checksums.

### Stage 1: inspection reasoning

- `src/features/outputs/pipeline.ts:102` loads submission/sections/answers/per-answer media, then request/vehicle (`:135`), performer (`:150`), and current OBD snapshot (`:194`). Raw answers passed downstream have ID, prompt, value, type, photo requirement, but no stable semantic field key, normalized metric, review state or evidence ID carried into output.
- Scope is read from the request (`pipeline.ts:192`). Dents & Tires receives adapter VIN solely as identity evidence and explicitly excludes OBD diagnostic content (`:207–211`). Preserve this when rendering a graphical template so limited inspections never appear to have checked mechanical systems.
- Gemini is hard-required before even adopting existing output (`pipeline.ts:92`); a provider-routing change must revisit this configuration gate. Private R2 is also required (`:84`).
- Existing standardized JSON for the same output version is adopted (`pipeline.ts:220–233`). Otherwise photos are best-effort loaded (`:235–247`), then `generateStandardizedOutput` receives raw data and image manifest (`:250–291`). Model output is inserted before coverage/PDF work (`:299`), allowing consumers to render JSON early.
- Photo loader (`src/features/outputs/inspection-photos.ts`) defaults to 16 photos (`:21`), 12 MB total (`:23`), 10 MB each (`:27`), batches four storage reads (`:28`), and a 45-second fetch budget (`:34`). Images on required-photo questions are preferred, then nonblank answers, then other images (`:90–108`). Videos are excluded. Failed/unsupported/oversized images are skipped (`:119–162`). Added placard, sidewall, tread, rim, body images can exceed these budgets; a simple global cap may drop the very evidence needed for a specific wheel. Per-field capture/extraction should preserve omitted/unreadable reasons.
- Current image manifest is only `{index, sectionType, prompt}` (`inspection-photos.ts:64`); persistent media ID/hash, wheel position, image quality, crop, extraction values, confidence, confirmation actor/time, and input version are absent.
- `src/lib/ai/standardized-generator.ts:7–25` requires each finding to be `{prompt, answer, severity}` and each section `{section_type, section_label, summary, condition_rating, findings, notes}`. Top-level fields are vehicle, metadata, performer, sections, diagnostics, overall summary, notable findings (`:57–81`). No bounded prose length or exact section coverage is enforced beyond the prompt; output strings/arrays are unbounded. Severity is `info|minor|moderate|major|critical`; condition is `excellent|good|fair|poor|not_applicable`. This cannot represent green/yellow/orange/red plus explicit uninspected/unknown as a typed observation.
- Prompt asks for all sections, treats notes as untrusted input, rates condition/severity, and says blank answers mean Not inspected (`src/lib/ai/prompts/standardized-output.ts:213–221`). It says photos are primary visual evidence, discrepancies should be reported, tread depth must not be measured from photos, and a photo alone is not proof of damage (`:229–238`). Those are useful intended safeguards, but semantic enforcement is mostly prompt-based.
- `src/lib/ai/gemini.ts:22` defaults to Gemini 2.5 Flash. It requests JSON then validates Zod (`:90–97`), uses one clarified retry for schema errors (`:105–124`), and exponential retries for 429 responses (`:128–132`). It does not record output model/prompt/schema version, latency, costs, normalized-input hash, calibrated confidence, or hard request timeout.

### Stage 2: warranty, not the requested page 2

- `pipeline.ts:349` routes Dents & Tires into `evaluateDentsTiresCoverage`; Complete goes to a second Gemini call (`:368`). The second-stage VSC determination stays independent of buyer-facing inspection insights.
- Dents & Tires coverage is deterministic but partly dependent on model prose: exact question prompts identify four tires, a combined wheel/rim field, and six body areas (`src/features/warranty/dents-tires-coverage.ts:61–76`). Tread ≤2/32 is covered and higher/unknown tread is excluded (`:134–162`). Damage comes from regex matching typed answers or non-info model findings (`:108–129`); wheel/body damage qualifies, bumpers are always excluded (`:165–201`). Healthy/no qualifying damage yields ineligible (`:204–213`). That is the product's coverage business rule, not a safety pass/fail indicator.
- The combined “rims or tires” field can currently drive the Wheels / Rims determination; a new per-corner tire-damage model should eliminate that ambiguity, with an explicit backward-compatible mapping.
- Complete's VSC prompt evaluates nine mechanical groups, excludes pre-existing conditions and wear items including tires, and marks not-inspected components limited (`src/lib/ai/prompts/vsc-generation.ts:53–79`, `:99–107`). Changing the report JSON can therefore change actual warranty results even if the PDF alone looks right.
- `src/features/warranty/actions.ts:45` builds purchasable warranty plans from `overall_eligibility` and component determinations. Ineligible means no plans, conditional selects two fixed tiers, eligible selects three fixed tiers (`:45–109`). `limited` component rows are not mapped to either inclusions or exclusions. Maintain current coverage policy unless user explicitly expands it; tire safety alerts should not automatically change contractual coverage.

## Recommended architecture to include in the plan

1. Introduce stable semantic question IDs plus an inspection-schema version. Preserve old prompt→ID adapters. Normalize numeric measurements with unit and original value, 4-digit DOT as a string (leading zero), tire size/service description, wheel position, status/unknown, evidence IDs, manual input versus extracted suggestion, and confirmation metadata. Snapshot verified evidence at submission so retries do not read later vehicle/profile edits as new facts.
2. Make extraction an earlier, cached per-photo step: capture placard and per-corner sidewall/tread/rim evidence; extract only visible markings/qualitative observations; let the inspector confirm or correct. Read tread from a gauge/manual measure; do not infer millimeters from an ordinary tire photo. Derive tire age as of inspection date, not PDF generation date. Unreadable means unknown and retake/manual input, never a clean result.
3. Implement deterministic checks over confirmed data for unit conversion, missing data, placard/actual comparison, approved tread cutoffs, immediate damage alerts, dry-rot and wear categories. Separate condition severity, evidence completeness, suggested action, and warranty determination. A not-inspected row must not become green by default.
4. Add reviewed facts/findings to a versioned canonical report object, retaining compatibility fields. A proposed Jev step should categorize normalized observations into controlled categories/status/action candidates and route ambiguity for review; use deterministic rules for hard thresholds and coverage. Verify vendor capabilities, supported modalities, schema constraints, latency and privacy from official docs before choosing it for extraction or replacing narrative generation. No live key required for this planning phase.
5. Create a dedicated fixed-layout, two-page renderer with explicit page objects: page 1 vehicle/inspection identity, status legend, selected checklist matrix, four wheel cards, body diagram and attestation; page 2 bounded insights grouped into a small set of categories and prioritized next actions. Use US Letter as current default, pending clarification. Share style tokens and geometry between scope variants; Dents & Tires must never show unchecked mechanical work as passed. The template can show uninspected/unknown distinctly or omit outside-scope groups visibly.
6. Make page 1 facts deterministic from verified data. Page 2 uses facts plus approved rule findings for concise insights, without “AI” wording in title/body. Keep source model/provenance internal. Suggested public title: Inspection Overview & Recommendations. Give prose fields exact length/line budgets, measure actual font layout, then summarize within budget. Do not silently truncate a safety issue or shrink body copy until unreadable to force two pages. Preserve exhaustive evidence in JSON/native detail and agree an overflow policy with the user.
7. Use a vector-capable PDF library/renderer that supports reliable text metrics, shape/color drawing, Unicode fonts, fixed page breaks and font embedding. Current hand-built simple-pdf is unsuitable without effectively reimplementing these. Preserve the existing VSC renderer if only the inspection PDF changes; current generator is synchronous Buffer-returning, so async library adoption requires updates to both pipeline body builders and fallback route.
8. Add final checkbox text version, actor ID, timestamp and submission/evidence revision to the atomic submit operation. Show inspector name/date and appropriate certification statement on page 1. Repeat confirmation when revising an inspection; do not manufacture a signature. Ask user whether typed name/signature or checkbox only is wanted.
9. Version report schema, template, rule set, prompt, provider/model and normalized input hash. Cache stages and record stage-specific errors/timings so retries don't pay for completed extraction/classification. Preserve existing artifact idempotence, checksum integrity, authorization and immutable prior versions. Historical missing fields display Not recorded; do not invent newly required measurements for old inspections.

## Concrete open questions affecting implementation

- Does “valuation” mean condition/severity categorization, warranty eligibility, repair-cost estimates, or dollar market value? Only the first two exist today. Monetary valuation needs separate data and requirements.
- Does exactly two pages permit the full detailed inspection to remain accessible in app/JSON while the PDF summarizes? What happens when many critical findings exceed the allocated insight space?
- Should both scopes use the same four-wheel capture module and per-wheel data? (Recommended.) How much must be required versus explicitly Unknown/Not accessible, including placard/inner-sidewall DOT evidence?
- Keep the current Dents & Tires scope/business rules (no bumpers, no diagnostics except VIN), or expand? Do not infer expansion from the generic example sheet.
- Checkbox only or typed name/signature too? Inspector attestation should be separate from any professional certification label.
- US Letter versus A4, and whether page 1 includes photo thumbnails or only schematic/evidence references; more photographs compete with the requested dense one-page graphical layout.
